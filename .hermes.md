# atoca.house — operating rules for Hermes

You maintain this repository. It is a GitOps repo: ArgoCD applies whatever
lands on `main` to the live Kubernetes cluster, so `main` is production.

Your checkout lives at `/opt/data/workspace/atoca.house` and is re-synced with
`origin/main` on every gateway restart.

## Before you change anything

1. Read `CLAUDE.md` at the repo root. It is the authoritative description of
   the layout, the per-application file pattern, and the conventions every
   change must follow (chart, naming, image pinning, Renovate comments,
   security context, storage classes, routing, 1Password-backed
   ExternalSecrets). Do not edit files here without it.
2. Load the `atoca-gitops` project skill (`/atoca-gitops`). It is the exact
   git and pull-request procedure you are expected to follow.

## Non-negotiables

- **Never commit to `main`, never push to `main`.** Every change goes on a
  branch and reaches `main` through a pull request that a human merges.
- **Always start from current `main`**: `git fetch origin && git switch -c
  <branch> origin/main`.
- **Always rebase before pushing**: if `origin/main` moved, rebase your branch
  onto it. Re-push a rebased branch with `--force-with-lease`, and only ever
  your own branch. Plain `--force` is blocked.
- **One topic per branch and per PR.** Small, reviewable diffs.
- **No credential material in the tree.** Values that must stay private are
  referenced through ExternalSecrets pointing at 1Password items; add the item
  first, reference it second.
- **You do not apply anything to the cluster.** `kubectl` here is read-only:
  `get`, `describe`, `logs`, `events`. Deployment happens through ArgoCD after
  a human merges your PR.
- **Verify before you open a PR**: YAML parses, the app directory has the files
  `CLAUDE.md` requires, image tags are pinned with a digest and carry the
  Renovate comment.

## Working style

- State what you changed, in which files, and what will happen in the cluster
  once it merges — including anything that restarts or has downtime.
- If a change is ambiguous or touches something you cannot verify, open the PR
  as a draft and say what you are unsure about.
- If a request would break one of the non-negotiables above, say so and propose
  the compliant version instead.
